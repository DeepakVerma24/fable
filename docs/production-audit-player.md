The wallet exposes FBU summary and immutable journal history, with no deposit, withdrawal, PSP, chargeback or cashier routes in the registered module. **Shared HTTP route.** Player components use TanStack Query. Requests go from browser to same-origin Next `/backend/*`, through the configured rewrite to Nest/Fastify, and back as JSON. The client includes credentials, buffers the full response into a string and parses it. The query client retries a failing query once by default. It provides in-browser query caching. A Next cache-components setting alone does not demonstrate HTTP caching of these browser requests. ### A. Sports event listing

The board independently requests the sport directory and event pages at 50 rows per request. It awaits each successive page before showing results, filters and sorts all returned records in JavaScript, then displays up to eight. It repeats the board query every 30 seconds while active. At the API, Zod validates parameters, then a synchronous array filter and slice produce each page. Events embed markets and some cricket scorecards. Database queries, indexes, locks, transactions and queues do not participate. Scaling the fixture array increases repeated scans, serialization, transfer, parsing and render work. A large directory would create a sequential page waterfall. See `apps/web/src/lib/sports.ts:38`, `apps/web/src/components/sports/sports-browser.tsx:19`, `apps/api/src/sports/sports.controller.ts:30` and `apps/api/src/http/page.ts:15`.

**Proposed test and change.** Compare the direct API and rewritten browser path with small and large synthetic catalogs. Record first-page bytes, requests per interaction, transferred rows, time to visible odds, JS parse/long-task time and latency percentiles. Move filters and paging to a bounded summary endpoint. Key public cache entries by normalized filters, page and representation version. Include scheduled/in-play state and primary odds only. Fetch scorecards on demand. A cold first page should require one listing request independent of catalog size.

### B. Event markets and odds

Event detail polls one complete event at 30-second intervals. A selected slip independently polls the full event on a 15-second interval and on focus under a different query key. A fresh placement additionally reads the event. The API performs a synchronous linear ID lookup and serializes the whole object. There is no DB join, lock, transaction, cache invalidation protocol, version, freshness deadline or queue. The static response cannot demonstrate provider freshness or cross-instance convergence. See `apps/web/src/app/(player)/sports/event/[id]/page.tsx:18`, `apps/web/src/components/bet-slip.tsx:24`, `apps/web/src/lib/bet-placement.ts:66`, `apps/api/src/sports/sports.controller.ts:41` and `packages/domain/src/catalog/sports.ts:275`.

**Proposed test and change.** Share public event keys and introduce a compact versioned quote/suspension representation with server timestamps and expiry. On command submission, validate the accepted version and price inside the authoritative financial operation. The current POST omits both. Benchmark event and market sizes, ETag hit/miss bytes, version age and p50/p95/p99. Exercise a synthetic price change between display and submit and require an explicit requote before reservation. A cached display price must never authorize money movement.

### C. Realtime odds delivery

The current gateway accepts a ping and synchronously returns an echo with permissive origin selection. Odds delivery currently uses the HTTP polling paths above. No per-update DB query, queue transit, fan-out indexing, replay cursor or stream-consumer latency can be measured in this implementation. For demand planning, the current polling component in requests per second is approximately active boards × pages/30 + event-detail views/30 + selected slips/15. Add navigation, foreground refetches, retries and pre-submit reads. Distinct views can overlap in one browser. See `apps/api/src/platform/platform.gateway.ts:7` and the interval sources in A/B.

**Proposed test and change.** Add a provider simulator first. Track provider event time, ingestion receipt, normalized sequence and browser application time. Publish per-market monotonic versions with suspension state. Bound per-connection buffers, coalesce superseded price updates, and require a snapshot if resume history expires. Restrict origins and subscription scopes. Measure updates/s, bytes/socket/s, lag, gap recovery time, dropped/coalesced messages, send-buffer size and reconnect storms. Keep the write path on PostgreSQL for financial decisions.

### I. Login and session validation

On the first mutation without a CSRF token the browser requests `/auth/csrf`, then posts credentials. The anonymous double-submit guard checks header against cookie. Login normalizes email, reads the unique user row, asynchronously derives a salted scrypt key with the libuv worker pool, verifies it with a timing-safe comparison, attempts the opening grant and upserts a fresh session. The session ID and CSRF token are generated independently and stored with a 12-hour absolute expiry. User lookup, grant transaction and session save are separate awaited operations. No remote identity provider or BullMQ job participates. Signup separately inserts the user before the grant and session save, so a connection failure can leave an account created without a successful response. A later login attempts the grant again. The browser then invalidates `me`. See `apps/web/src/lib/api-client.ts:26`, `apps/api/src/auth/auth.service.ts:54`, `:66` and `:89`, `apps/api/src/auth/password.ts:20` and `packages/database/src/prisma-player-store.ts:15`.

Every protected call reads session by primary key, then user by primary key, sequentially. The Prisma lookup retrieves the full player record including password hash before projection. Reading an expired session triggers a delete, so concurrent requests may race on single-row deletion. There is no requested limit/queue for password-verification concurrency. The process-local rate limiter and KDF capacity can dominate p99 at login peaks. See `apps/api/src/auth/guards.ts:28`, `packages/database/src/prisma-player-store.ts:20` and `:71`, and `apps/api/src/http/rate-limit.ts:3`.

**Proposed test and change.** Fetch minimal session/public player fields with one expiry-filtered query. Expire sessions from an indexed maintenance path. Keep revocation authoritative. Remove routine grant posting from login/GET once a separately recoverable, idempotent onboarding contract exists. With dedicated accounts in an isolated DB, split valid lookup, expired lookup, login success/failure and first grant. Measure KDF queue wait/CPU, query count, pool wait, DB transaction duration and edge p50/p95/p99. Verify expiry races return 401 and logout causes the next protected call to fail on every replica.

### J. Bet and transaction history

The wallet screen independently fetches wallet and all bets. The bet history list fetches all signed-in user records, filters and sorts on the client. The detail screen searches the same list for one ID. SQL filters by user and sorts a JSON timestamp with no limit. Transaction history requests ten records per page, while the server first performs the grant attempt, loads global journal entries and account relations, filters them in application memory and only then slices. Expanding a detail can increase cost with the user's entire betting history, and a quiet player's transaction read can increase with total platform activity. Neither route uses a background job. See `apps/web/src/app/(player)/wallet/page.tsx:13`, `apps/web/src/components/sports/bet-history.tsx:19` and `:44`, `packages/database/src/prisma-bet-store.ts:9`, `apps/api/src/wallet/wallet.controller.ts:27` and `apps/api/src/wallet/wallet.service.ts:64`.

**Proposed test and change.** Add ownership-qualified detail reads and stable keyset paging with an indexed typed creation time and ID tie-breaker. Restrict ledger history reads to the player's available/held account IDs in SQL. Obtain all lines required to explain the selected journals without exposing another player's data. Measure query plans, rows/blocks touched per returned item, payload size, DB pool wait and p95 with a fixed player's page and increasing unrelated ledger volume. Verify the imported and new journal totals, ordering across equal timestamps, account switching and cross-player denial.

## Security and recovery release gates

1. **Shared-browser disclosure — high.** The slip stores pending requests under one browser-origin key. It renders the previous player's stake and selection before comparing the pending player ID with the viewer. Only the retry button is disabled for a different player. Wallet, recent bets on the wallet page, and transaction-page caches also omit the player ID. Login and logout invalidate only the session query. Account-switch stale rendering is a source-supported risk. Logout navigates away even when server revocation fails. Scope account data and recovery display by authenticated player, clear/cancel account-bound queries on principal change, synchronize sign-out across tabs and surface failed logout. Gate with two synthetic players, delayed responses and a signed-out browser. Assert no prior stake, selection, receipt or balance renders at any frame, while the original player can still recover with the same key. See `apps/web/src/lib/bet-slip.ts:6`, `apps/web/src/components/bet-slip.tsx:217`, `apps/web/src/components/shell/use-session.ts:24`, `apps/web/src/app/(player)/transactions/page.tsx:15`, `apps/web/src/components/auth/auth-form.tsx:140` and `apps/web/src/components/shell/user-menu.tsx:68`.
2. **Uncertain-response handling — high.** A retry entered with a pending bet leaves it pending even if the server issues a definitive rejection. The client then locks editing against that browser-wide pending command. A lost acknowledgment after commit legitimately requires the same key. Introduce an authenticated operation-status contract retaining the original fingerprint, terminal result and rejection semantics. Preserve the existing key throughout recovery. Verify refused-before-commit, committed-with-lost-response, account switch, expiry and terminal conflict. See `apps/web/src/lib/bet-placement.ts:44` and `:118`, and `apps/web/src/lib/bet-slip.ts:164`.
3. **Edge trust, abuse controls and private HTTP data — high.** Fastify enables unrestricted proxy trust and listens on all interfaces. Registration reads the first forwarded address directly. Secure-cookie selection also consults the forwarded protocol. Cookie-based CSRF guards and a CORS allowlist are present. Per-address or per-email rate buckets live in a growing process map and limits multiply across instances. Readiness for internet traffic requires a known proxy chain, sanitized forwarding, production secure-cookie policy, origin restrictions, distributed bounded rate limiting and KDF admission limits. Set private/no-store headers for authenticated wallet, bet and identity responses through the proxy. Casino recovery GETs already do this. Verify from the intended ingress and direct-origin network boundary. See `apps/api/src/main.ts:19`, `apps/api/src/auth/auth.controller.ts:70`, `:84` and `:162`, `apps/api/src/http/cookies.ts:33`, `apps/api/src/http/rate-limit.ts:3` and `apps/api/src/casino/originals.controller.ts:64`.
4. **Application and identity defenses — high before privileged or regulated use.** API security headers use Helmet with CSP disabled. Swagger is registered unconditionally. The Next configuration inspected supplies no application CSP. The observed SQL paths use tagged/parameterized SQL for dynamic values. The raw health check uses a constant query. Catalog/provider code supplies fixed fixtures with no remote vendor fetch. These observations give limited source assurance. Gate a nonce-compatible browser CSP with report-only validation first, restrict operational endpoints, enforce explicit authz on privileged actions, and retain parameter binding and outbound allowlists when introducing integrations. Harden credential recovery, MFA/step-up, revocation, session ID digest-at-rest and auditable staff access. Test account A/B isolation, operator denials, session expiry/revocation and masked telemetry. See `apps/api/src/configure-http.ts:10`, `apps/web/next.config.ts:5`, `packages/database/src/prisma.ts:13`, `packages/database/src/prisma-player-store.ts:54` and `packages/domain/src/providers/provider.ts:14`.
5. **Licensing, policy controls and fraud — blocked for real money.** Account-level ownership is present. Operator/tenant scopes, verified age/identity, geolocation and jurisdiction eligibility, AML/fraud case handling, self-exclusion, player limits, cooling-off, certified provider integrations and associated evidence/retention flows were absent from the inspected user schema and registered controllers. A demo stake range is a technical input bound. No jurisdiction, licence, payment data scope or certification was established. Before any future real-money design, obtain an approved jurisdiction-specific control matrix and define policy authority, operator isolation, enforceable eligibility/limits at acceptance, stop-play propagation, durable decisions and independent testing. Keep simulation controls and labels in force. See `packages/database/prisma/schema.prisma:32`, `apps/api/src/auth/guards.ts:25`, `apps/api/src/player/player.module.ts:28`, `packages/domain/src/wallet/demo-wallet.ts:4` and `apps/api/src/config/env.ts:42`.
