# FABLE operations, security and disaster recovery audit

**Revision:** `49d0c862fa6adf69c83cdd3b65179be7a993b8af`. **Review date:** 9 November 2026. This appendix distinguishes checked-in behavior from proposed launch gates. It covers repository-controlled infrastructure. External infrastructure, account permissions and equivalent controls operated outside this repository require separate evidence.

## Network and release topology

**Container routing defect.** Player requests use the same-origin `/backend` prefix. Next builds its rewrite destination from `API_URL`, which defaults to `127.0.0.1:4307`. The web image builds without supplying that value. Compose injects the different variable `NEXT_PUBLIC_API_URL` at runtime. In a separate web container the compiled default points back into that container. A successful native-machine browser test can therefore coexist with a broken container deployment. This finding follows from configuration and network namespaces. Docker was unavailable on this audit's PATH. [Browser client](../apps/web/src/lib/api-client.ts#L45) · [Next rewrite](../apps/web/next.config.ts#L3) · [web build](../apps/web/Dockerfile#L10) · [Compose web service](../docker-compose.yml#L105)

**Acceptance.** Route the browser through one public origin and forward API requests through private service discovery or a controlled reverse proxy. Exercise the packaged standalone image on the same network boundary planned for release. Verify event data, CSRF issuance, authenticated wallet reads and cookie attributes through the public origin. Test correct behavior when the API is removed from rotation. Keep database, broker, metrics and operational endpoints private.

**Infrastructure evidence.** The Terraform module contains only local descriptions of intended services. The dev, test and prod entry points reference that module. Compose runs a single PostgreSQL, transaction pooler and Redis. Infrastructure ports are published and the database uses development credentials. API and worker images install production packages in a second stage. The web image copies Next standalone output. None of the three Dockerfiles selects an unprivileged runtime user or pins its base image by digest. Root build contexts use `COPY . .`. The Docker ignore file excludes several common inputs but omits local audit logs, the local tool directory and wildcard environment overrides ignored by Git. These are exposure paths in build contexts and intermediate caches. Presence of credentials in an image was not tested. [Terraform module](../infra/terraform/modules/platform/main.tf#L1) · [local services](../docker-compose.yml#L6) · [API image](../apps/api/Dockerfile#L7) · [worker image](../apps/worker/Dockerfile#L7) · [web image](../apps/web/Dockerfile#L7) · [Docker ignore rules](../.dockerignore)

**Release target.** Run stateless Next and API replicas behind a TLS load balancer across fault domains. Keep the modular API and separate worker processes. Use a bounded PostgreSQL connection budget, one fenced writer and a tested standby. Isolate Redis broker capacity from evictable read caches and rate-limit counters. Define restricted service identities, egress rules, quotas, resource requests, scratch storage, secrets rotation and image provenance. Gate a release on service discovery, non-root operation, an allowed-files build context, image and secret scans, readiness, graceful draining and a reversible compatible application rollout. Exercise loss of one replica and one fault domain before inferring availability.

## Queues, cache and realtime

**Actual implementation.** The worker connects to `fable.jobs` when Redis is configured. Without a URL it logs and waits for shutdown. Its only successful job is `platform.ping`. It rejects wallet mutations and unknown job types. A failure listener logs the error. No application publisher, business retry/backoff policy, durable consumer deduplication, dead-letter handling or relayer was found. The Redis helper's connection retry settings concern network commands and do not implement job delivery guarantees. Local Redis disables both persistence mechanisms. The Socket.IO gateway accepts a ping and echoes its body. It allows reflected origins and has no odds message, stream cursor, subscription authorization, slow-consumer policy or scale-out adapter. No provider transport or feed timestamps exist to measure lag. [Worker](../apps/worker/src/main.ts#L14) · [allowlisted job handler](../apps/worker/src/processor.ts#L25) · [Redis connections](../packages/database/src/redis.ts#L4) · [Redis configuration](../docker-compose.yml#L44) · [gateway](../apps/api/src/platform/platform.gateway.ts#L7) · [provider adapter](../packages/domain/src/providers/provider.ts#L14)

**Cache contract.** Public catalog pages and versioned market snapshots are candidates for CDN or Redis caching. Key by the dimensions that change the result, including competition, normalized filters, page, format and feed version. Bound cardinality and implement expiry plus versioned invalidation. Rebuild from the authoritative source after Redis loss. Never share personal response caches across players. Session validity and revocation, active round state, placement idempotency, committed wallet balances and settlement decisions require PostgreSQL authority. Revalidate the market version, price and suspension at acceptance. The current frontend query provider sets one retry and disables refetch on focus. Those browser choices provide neither a cross-process cache nor feed freshness guarantees. [Browser query provider](../apps/web/src/components/providers.tsx#L6) · [ledger store](../packages/database/src/prisma-ledger-store.ts) · [casino session store](../packages/database/src/postgres-original-sessions.ts)

**Reliable events.** For future notifications, write the event ID, aggregate ID/version and minimal payload to an outbox in the transaction that commits the underlying event. Have a separate relayer publish with bounded retries, jitter, expiry and visibility into oldest unpublished age. Record stable consumer IDs and the completed effect under a unique key before acknowledging. Replay after broker loss from retained PostgreSQL records. Quarantine exhausted or invalid jobs with restricted access and operator-approved replay. Specify retention and erasure of personal data in messages. Keep money mutations inside the financial service and its existing transaction boundary. Test crashes before enqueue, after enqueue and after durable processing. Each scenario must recover the intended effect once and preserve journal and audit invariants.

**Future odds fan-out.** Normalize upstream snapshots/deltas with source timestamps and a per-market sequence. Detect gaps, suspend stale markets and recover from a snapshot plus cursor. Distribute public changes by room, coalesce superseded prices, and cap subscriptions, payload size and pending bytes per connection. Persist the history necessary to support the reconnect window or explicitly return a fresh snapshot when a cursor expires. Keep replayable account events separate from lossy public ticks. Validate client origin, authentication where appropriate and subscription authorization at every replica. Instrument provider age, ingestion queue age, processing lag, delivery gaps, client-observed freshness, dropped updates and reconnect rates. An isolated test should disconnect a subscriber and a gateway under load, force a sequence gap, restore the current snapshot and demonstrate bounded memory for slow readers. Ping success provides no evidence for odds fan-out capacity.

## Identity, perimeter and regulated controls

**Existing protections.** Password hashing uses asynchronous scrypt, a random salt and a constant-time digest comparison. The session token and CSRF token are random and independently generated. The HttpOnly session cookie has a 12-hour lifetime and SameSite=Lax. The anonymous-form CSRF guard matches a cookie and header. Authenticated writes use a header checked against the database session token. An authentication guard resolves the session owner on the server. The API configures Helmet and a credentialed CORS allowlist. The production code fixes real-money mode to false. These are source findings, with the usual distinction between configured controls and what the deployed proxy actually enforces. [Password implementation](../apps/api/src/auth/password.ts#L21) · [session creation](../apps/api/src/auth/auth.service.ts#L89) · [guards](../apps/api/src/auth/guards.ts#L25) · [cookies](../apps/api/src/http/cookies.ts#L28) · [HTTP configuration](../apps/api/src/configure-http.ts#L8) · [mode](../apps/api/src/config/env.ts#L35)

**Gaps that affect horizontal scaling.** Authentication and casino throttles use a process-local Map with no expiry of inactive keys. Login is keyed by email, and registration derives its address directly from the first forwarded IP. Fastify trusts every proxy. Cookie security accepts the forwarded scheme. A multi-replica deployment therefore lacks a common rate budget and depends on ingress sanitization. A valid session is read using a token stored directly in the DB. Finding an expired session can delete its record as a side effect of a read. Concurrent expiration can race in the single-row delete. Test this failure mode with isolated fixtures. Establish private origins, an explicit trusted proxy chain, production TLS-only cookies, credential rotation, protected session-token storage, idempotent cleanup and distributed rate limits with bounded TTL and documented outage behavior. Verify shared limits and cookie flags across replicas. Add edge admission controls and bounded password verification concurrency. **Authorization and web exposure.** The inspected code supports player ownership checks. It does not establish staff identities, role grants, tenant isolation, MFA, password/account recovery, privileged action approvals or production operator access reviews. The API explicitly disables Helmet CSP and mounts Swagger unconditionally. No frontend CSP was found in the Next configuration reviewed. No application use of `dangerouslySetInnerHTML` or a player-controlled provider destination appeared in the source search. The unsafe-named query in the database health helper runs fixed SQL. These observations cover inspected paths only. Before public exposure, add CSP compatible with the rendered frontend, operational endpoint access control, deployment-specific CORS and outbound address allowlists. Review every future raw SQL and provider transport boundary. Validate mirrored proxy headers, object ownership, session revocation, constraints on browser script execution, and rejection of unknown destinations in a staging environment. **Fraud, privacy and gaming.** No checked-in production cashier, fraud decisioning, age/identity proofing, AML review, geolocation enforcement, self-exclusion registry or centrally enforced responsible-gambling limits were identified. Browser notices and single-request stake validation cannot enforce those policies. Missing integrations also mean there is no observed real deposit processing, live-dealer operation or licensed feed to certify. Decide target jurisdictions with counsel and the operator. Map each intervention to onboarding, session, wagering and cashier boundaries. Design auditable policy versions, exceptions, retention, restricted investigator access and action on unavailable or stale eligibility checks. Require negative tests for excluded users, eligibility changes and cumulative limits across simultaneous requests. Determine applicable certification, recordkeeping and provider rights for each market. For future payment processing, determine card-data scope with the payment provider and assessor before selecting an integration. ## Disaster recovery and incident acceptance

GitHub subsequently confirmed success for the reviewed commit's Windows portability, Linux verify and financial PostgreSQL jobs. Linux verify includes migrations, build, casino recovery, Playwright and Terraform validation. These hosted results establish the candidate's CI status. The staging, load and restore gates below still require separate exercises. [Workflow run 9](https://github.com/DeepakVerma24/fable/actions/runs/42517324476)

The repository shows one persistent local PostgreSQL volume. It provides written financial migration safeguards, including a writer drain for the whole hardening chain, an exclusive preflight, bounded lock windows, restricted roles and a forward-correction procedure. The financial report calls for independent restore rehearsal. It does not supply a completed backup restore or operational failover test. No configured WAL archive, automated standby promotion/fencing, Redis HA, scheduled backup verification, on-call rotation or deployment orchestrator was found in the checked-in infrastructure. [Local persistence](../docker-compose.yml#L7) · [migration cutover procedure](phase-7-1-remediation.md#L34) · [casino recovery verification and limits](casino-recovery/IMPLEMENTATION.md) · [Terraform](../infra/terraform/modules/platform/main.tf)

Proposed release gates, to be run only in a separately provisioned environment with synthetic data:

1. **Backup and PITR.** Assign owners and approved RPO/RTO per fault class. Require every acknowledged financial write to survive a supported single-primary failover. State the distinct disaster-region recovery objective and when the platform must keep financial traffic closed. Take encrypted full/base backups plus WAL with access separation and integrity checks. Restore to independent infrastructure and a chosen timestamp. Record elapsed restore time and actual recovery position. Verify journal sums, wallet derivations, outstanding reservations, audit links, idempotent replays and casino round revisions with historical expected control totals.
2. **Failover.** Stop or isolate the writer under a bounded synthetic workload, fence the prior primary, promote through the intended HA mechanism, reconnect clients/poolers and reconcile all acknowledgements and uncertain responses. Validate the declared RPO/RTO and prohibit dual writers. Route authoritative wallet, settlement, active round state and immediate post-write reads to the primary. Consider lag-gated replicas for analytically tolerant reads only after measuring replay lag.
3. **Broker and cache loss.** Lose Redis and then a worker, accumulate a known backlog, restart services and record rediscovery and drain times. Verify that quotas degrade according to policy, unsafe requests are denied when required, caches rehydrate and durable events can be replayed. Reconcile effect IDs against known input counts and monitor maximum queue age during recovery.
4. **Migration and deployment rollback.** Rehearse the exact chain on a restored, representative-size copy, measure locks and drain time, and verify abort-before-partial-activation. Deploy compatible changes as expand/migrate/contract where proven safe. The current financial hardening explicitly needs coordinated writer drainage. Roll back compatible binaries or roll forward under a write freeze while keeping ledger protections intact. Gate version changes on compatible schema, readiness and real cross-container smoke results.
5. **Incident response.** Assign incident commander, database owner, security owner and communications lead. Produce and exercise procedures for lost acknowledgement, overdue holds, reconciliation mismatch, stale provider feed, exposure of session credentials and exhaustion of storage. Include a tested writes-off switch, evidence retention with access controls, status channels, escalating burn-rate alerts, corrective accounting and post-incident review. Require signed drill evidence, remediation of failed checks and a repeated successful drill before launch.
