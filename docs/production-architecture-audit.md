# FABLE production readiness and low-latency architecture audit

**9 November 2026 · local revision `49d0c862fa6adf69c83cdd3b65179be7a993b8af` · production decision: NO-GO.**

FABLE has a working simulated player experience and a substantial transactional core. Its first production constraints are observable in the code today. Changed accounts can see stale private data in the browser. A wallet read can initiate a posting and retrieve every player's journals. A new bet performs that same global read while holding a serializable transaction. The web container's API rewrite defaults to its own loopback. Durable casino practice rounds are materially further along than live odds delivery, operator tooling, or disaster recovery.

## Decision record

1. **Block a shared-player pilot on identity isolation.** The server scopes the investigated reads and commands by player. The browser uses global wallet and history keys and can display stored pending stake/selection before checking its owner. Switching accounts, an unconfirmed logout and in-flight responses are the relevant cases. This is a source-confirmed design defect. Frequency in real sessions was not measured. [Player review](production-audit-player.md)
2. **Block scale certification on the ledger read paths.** Every unrelated account grows the data a wallet GET and a new bet can deserialize. Within a serializable bet this also broadens predicate reads and prolongs contention. The trigger-level funds and journal checks must survive optimization. Measure betting latency through the database commit acknowledgement and replay uncertain results with the same key. [Database review](production-audit-database.md)
3. **Block a production topology claim on routing, recovery and observability.** A successful single-host build or health ping does not exercise the standalone Next rewrite between containers, pool failure, failover, business endpoint latency or a restore from archived WAL. No production resources are provisioned by the checked-in Terraform module. [Operations review](production-audit-operations.md)
4. **Keep sportsbook prices and Originals classified as simulation.** Game state is durably persisted and server-generated. Sports data, scores and prices are fixtures. There is no operational feed, private odds stream, approved cashier, certified game integration or jurisdiction decision in the examined sources. A 10k–100k socket plan is a dimensioning exercise only. [Player review](production-audit-player.md) · [Performance plan](production-audit-performance.md)

## Prioritized implementation roadmap

Each sprint has a gate. Sprints 1 and 2 can staff independent tracks once identity and ledger interfaces are agreed. No cross-service decomposition is required.

1. **Player-private, bounded financial reads.** Objective: eliminate cross-account display and the unbounded work on the financial critical path. Scope, dependencies, risks, tests and exit are detailed in the specification below. This gate applies to the simulated environment too.
2. **Production-like staging and recovery baseline.** Platform/SRE supplies separate storage, two API instances, private networking, web routing, a transaction pool, a matching major PG version, read-only monitoring, liveness/readiness and build provenance. Depends on a hosting decision, secret custody and volume limits. Risk is a nominally green health endpoint hiding broken player traffic. Verify full browser-to-API requests across containers, pool starvation, lost commit responses, point-in-time restore, restart and role restrictions. Exit with a known-good release artifact, measured RPO/RTO, current CI and an on-call rollback drill.
3. **Identity, operational control and reconciliation.** Security and finance owners define player/operator roles, step-up MFA, session revocation, abuse budgets, identity recovery and independent ledger reconciliation with an exception queue. Depends on a policy owner, data retention and staging. Risk is overprivileged admin access or a compensation that causes a second posting. Verify two-person approvals, negative authorization tests, bounded account abuse, hold ageing, duplicate replays and an exception drill. Exit with access reviews, evidence retention and reproducible end-of-day checks.
4. **Sports read model and quote contract.** Sports team introduces normalized, versioned simulated event/market records, compact pages, current-state checks and a defined accepted-price policy. Add source timestamps, suspensions and event-result deduplication before any real feed. Depends on stable player/financial APIs and a feed contract or synthetic simulator. Risk is accepting obsolete prices or settling twice after a correction. Test stale/closed/duplicate/out-of-order inputs, replay after restart and reconciliation. Exit with current-version checks at acceptance, bounded page work and measured read SLOs.
5. **Asynchronous delivery and realtime.** Add the outbox to the producing transaction, idempotent projection consumers, bounded Redis delivery, rooms, resume tokens, snapshots and DLQ/redrive. Depends on stable event identities and versioned read models. Risk is dropped or out-of-order delivery during reconnect or broker failure. Verify crash before/after publication, slow clients, feed lag and backlog drain. Exit when consumers converge to the authoritative sequence with zero duplicate business effects.
6. **Capacity, hardening and controlled pilot.** Run the tiered performance plan, canary rollback, restore, regional failure and incident rehearsals. Budget CPU, pool slots, lock queues and fan-out separately. Depends on production-like topology, realistic data/skew and current security gates. Risk is coordinated omission or a passing average masking money-path failures. Exit per endpoint p95/p99/error budgets, bounded backlog and post-run ledger/casino reconciliation at each authorized tier.
7. **Conditional regulated-product programme.** Product, compliance and licensed partners determine markets, products, age/identity verification, exclusions, financial-crime controls, payment scope, testing, reporting and required independent approvals. Discovery can run in parallel. Any implementation depends on written jurisdiction and provider decisions. Risk is assuming one market's rules or simulation tests qualify a different product. Exit from planning requires a signed control matrix, named owners and separate authorization. The present system remains simulated. [Example jurisdiction-specific technical standards](https://www.gamblingcommission.gov.uk/licensees-and-businesses/guide/remote-gambling-and-software-technical-standards) · [PCI DSS scope and standard](https://www.pcisecuritystandards.org/standards/pci-dss/)

## Immediate sprint specification

**Scope:** account-private, read-only wallet/history and bounded queries inside existing simulated bet transactions. The two defects intersect on the exact pages that fetch journal data after login, placement and account change. Owners are one backend/database engineer, one player engineer and one QA/SRE engineer. First dependency is an isolated volume with space for the largest planned dataset, WAL, build artifacts and recovery margin. Confirm free space on every relevant filesystem. Current C: is inadequate.

**Contract and changes to prepare**

- Extend the domain store through transaction-bound primitives for (a) one account-pair balance in FBU, (b) an owner's journal page or journal detail, (c) exact journal lookup by scoped reservation/settlement keys and (d) owned bet page/detail. Implement both PostgreSQL and demo-memory adapters while retaining independent full replay for reconciliation. Bind every decision inside placement/refund to the same SERIALIZABLE transaction. Financial reads go to the primary.
- For balance, select wallet and hold account codes for the authenticated user, then conditionally sum signed integer minor units by currency in **one statement/snapshot**. Return explicit zeroes for unused accounts as required by the agreed opening-grant semantics. Preserve arbitrary-precision arithmetic and wire strings. For history, locate distinct owned journal IDs first, sort/cursor by stable time and ID, then join the complete lines for the bounded page. Wallet-to-hold transfers must appear once. Preserve previous net-from-available semantics and immutable identity.
- On register use an atomic or durably recoverable idempotent opening grant, with a retryable authenticated recovery path for legacy/uninitialized demo accounts. Establish which older accounts already received grants. Define distinguishable pending initialization semantics and verify a failed response can resume without duplicate credit. Remove grant attempts from wallet and history GETs only after compatibility tests. Apply complete owner checks and private/no-store headers to private reads. Avoid shared caches of monetary values.
- Replace the bet pre-check's full ledger enumeration with the scoped balance primitive and the refund filter with lookups of both original journals. Retain database nonnegative checks, posting-XID sealing, uniqueness, fences, bounded conflict retries, atomic status/audit and deterministic replay. Model an unaffordable post-settlement refund as an explicit reconciliation case. Bubble terminal errors with safe diagnostics.
- Introduce typed timestamps or compatible indexed expressions for bet history if plans justify them. Use stable keyset pagination with a bounded maximum and owner-filtered detail. Migrate the old list clients in the same release or version the endpoint. Review legacy JSON timestamps and time-zone semantics before any index, backfill or cutover. Do not rewrite applied migrations.
- Scope query keys for wallet, bets and transactions to the authenticated player; gate rendering while identity is unknown. Cancel active requests at logout and on session/account change, clear private cached results, reset stale pending UI and coordinate across tabs. Store pending slips by owner, migrate a validated legacy pending record without showing it to a different owner and retain safe same-owner uncertain retry. An unsuccessful logout requires an accurate state and retry. Never create a fresh bet key to resolve an uncertain commit.
- Instrument query counts, fetched rows, serialized bytes, transaction duration, pool wait, lock wait, retry code/attempt and committed-versus-replayed result through low-cardinality dimensions. Keep player identifiers, raw idempotency keys, cookies and stakes out of metric labels. Retain a redacted correlation ID for investigation.

**Verification and release gate**

1. Use two independently started APIs, a real isolated PostgreSQL primary, a direct migration role and a restricted runtime role. Generate small, large and hot-account fixtures on dedicated storage. Compare old full replay against new queries at the same ledger watermark for grant, win/loss, reserve, cancellation, release, refund, empty and legacy cases.
2. Demonstrate that repeated authenticated GETs cannot post a grant or change ledger/audit rows. Use a read-only database transaction or restricted read role for the query itself. Separately cover the session expiry path, which can currently delete a row on a GET. Include stable pagination under concurrent additions, multiple same-timestamp journals, wrong-account detail, and missing or malformed cursors.
3. Race same and different keys, same/different players, debit from wallet and hold, rollback before commit and a dropped response after commit. Require exact original placement replay, one expected posting set per operation, zero negative balances, balanced currencies and complete status/audit linkage for every run. A serialized retry or safe business rejection is observable.
4. In a browser test log in as A, leave data and an uncertain bet, switch to B in this tab and a second tab, navigate Back and restore A. Inject a delayed response from A and a failed logout. Neither B nor a signed-out viewer may see A's stake, history, wallet, result or recovery details. A must be able to recover the same command safely.
5. Record before/after SQL plans and actual buffers on disposable data, service percentiles, end-user completion, error mix, attempts and pool/lock waits as unrelated journals grow at fixed owner activity. Require disappearance of global hydration and stability against unrelated-user growth. Pilot targets are wallet p95 <150 ms and placement p95 <250 ms at the agreed baseline offer rate. A missed target remains an open gate. Publish raw distributions, commit/fixture hashes and environment.
6. Require fresh Linux/Windows checks, production builds, financial PG regressions, casino process recovery and browser regressions on one candidate. Reconcile before/after totals and rehearse application rollback across any additive migration. The resulting evidence qualifies only the tested simulated release and load profile.
