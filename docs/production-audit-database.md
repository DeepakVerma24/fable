## Verification boundary

A client attempted a loopback connection to the previously verified PostgreSQL fixture on port 55437 to issue `BEGIN READ ONLY` and six small `EXPLAIN` statements. The connection returned `ECONNREFUSED` before any SQL ran. A TCP check against the Compose direct port 54329 timed out after 1.5 seconds. Local process/service and listening-port checks found no PostgreSQL server on the expected endpoints. No database was started. C: free space fluctuated down to 12,611,584 bytes during inspection. No measurements of database latency, CPU, lock waits, plans, rows touched, buffer hits, failover or TPS were obtained in this audit. The scans and sorts described below follow from the source query shapes. Planner choices depend on statistics and data distribution.

The earlier casino handover records PostgreSQL 18.6 on loopback, five applied migrations, 37 passing financial PostgreSQL regressions and five database-backed casino tests. Five further process-recovery scenarios used four API processes. That is historical evidence for tested invariants and application process loss. ## Request paths

The browser calls `/backend` through a Next rewrite to Nest/Fastify. JSON responses go through text decoding and parsing on the client. A mutation without a cached CSRF token may first call `/auth/csrf`. Each protected API call performs sequential session-primary-key and user-primary-key lookups. Looking up an expired session can delete it. Production-style database traffic would add the PgBouncer hop when configured as in Compose. The six paths below await database completion and use no background worker, Redis lock or distributed response cache. The number of Prisma wire statements for nested reads/inserts requires actual tracing. ### D. Single-bet placement and internal transitions

- **Observed.** The browser takes a Web Lock, verifies the account via `/auth/me`, obtains current event/market terms for a fresh submission and persists player, stake, selection and request key before `POST /demo/bets`. Browser timeout is 15 seconds. A retry retains the earlier key. The POST uses session and CSRF guards. The server's immutable request fingerprint includes selection and stake. It checks the current static board, enforces suspension/closed-event restrictions, derives available FBU and applies a deterministic outcome. The public route uses immediate reservation and settlement. Acceptance, cancellation, separate settlement and refund exist internally. A live provider price/version or result identity is absent. [Submission](../apps/web/src/lib/bet-placement.ts#L29) · [Controller](../apps/api/src/sports/bet.controller.ts#L35) · [Domain](../packages/domain/src/sportsbook/bet-operations.ts#L20) · [Quote lookup](../packages/domain/src/catalog/sports.ts#L279)
- **Database work.** Within one Prisma SERIALIZABLE transaction the store probes the hardening marker, takes a transaction advisory lock per player and reads the player/key row FOR UPDATE. An identical replay returns the immutable original placement, including after a transition. Changed terms conflict. A miss checks legacy journal keys before any new postings. A fresh placement hydrates **every** journal with entries/accounts, flattens these objects, and scans them for the player's account while the transaction remains open. Each journal rechecks readiness/key, locks its distinct account codes in sorted order, finds/creates each account, inserts header/lines, includes relations and inserts an audit row. It serializes the bet JSON and writes its own status audit in that transaction. Refund again enumerates all journals to find the original pair. A repeated transition to the existing status has no additional financial effect. [Transaction](../packages/database/src/prisma-bet-store.ts#L21) · [Ledger store](../packages/database/src/prisma-ledger-store.ts#L52) · [Refund](../packages/domain/src/sportsbook/bet-operations.ts#L98)
- **Tail risk.** The global read grows with unrelated players and widens the serializable dependency footprint. There are sequential per-distinct-account round trips and repeated trigger aggregates. The house fence serializes postings that share that account. Lock ordering applies per journal. A composite workflow can acquire more locks at later steps. Up to five attempts include backoff. A single bet attempt permits 10 s acquisition and 15 s transaction time. The server can still be resolving the original request after a browser timeout. A refund of a winning bet can fail when the recipient has already spent the winnings. Require an explicit operational exception policy and keep the wallet nonnegative.
- **Proposed change and test.** Read authoritative balances by account on the same primary transaction and locate journal pairs by unique idempotency keys. Preserve the legacy-key fence, response immutability, append-only corrections, DB triggers and transaction-wide commit. On a future changing odds feed, require a server-validated quote ID/version and explicitly accepted price before committing. Profile distinct-key contention for one wallet, independent wallets sharing a house, duplicate requests, spent winnings, failed audits and lost commit acknowledgement. Compare p50/p95/p99, retries by SQLSTATE, lock holders/waiters, query counts, transferred rows and committed effects. The proposed placement target is p95 <250 ms at the API. Report browser-visible latency separately.

### F. Casino round creation

- **Observed.** The browser serializes local actions via Web Locks, checks `/auth/me`, saves an operation and submits it. After success it refetches history. A new command checks out the separate casino pool (maximum 10, connect timeout 5 s), begins READ COMMITTED, sets local lock/statement deadlines (2 s/8 s), takes a per-player transaction advisory lock, reads the database namespace, probes the player/request-key PK and reads the DB clock on a miss. Mines also checks the single active board. The server uses cryptographic random integers and writes public JSON, private board and command replay JSON together. Constraints and triggers enforce game/version/status and match the exact replay to its round revision. Dice, Plinko and Limbo complete at creation. Mines starts active. Committed effects never touch the wallet. [Store](../packages/database/src/postgres-original-sessions.ts#L115) · [Rules](../packages/domain/src/casino/originals.ts) · [Controller](../apps/api/src/casino/originals.controller.ts#L94) · [Command pairing](../packages/database/prisma/migrations/20261105200000_casino_sessions/migration.sql#L110)
- **Cost and test.** Queries are bounded per command, but serial round trips, JSON encoding/validation, command snapshots, pool wait and commit WAL affect latency. The lock queues unrelated Originals for the same player. A correct replay skips RNG, round insertion and new command write. Stage many independent players, a single-player burst, simultaneous Mines starts, same-key and changed-payload retries. Measure endpoint vs click-to-render, pool wait, commit time, command bytes/WAL and fairness across players before merging any redundant query. No seeded random source should enter the running API.

### G. Mines reveal or finish

- **Observed.** Same auth, CSRF, namespace and replay path as creation. With a new key the transaction reads only that player's round FOR UPDATE, validates schema and advances the private board on the server. The conditional UPDATE requires active status and expected revision. Both the round update and immutable response history commit before success. Each mutation encodes a public snapshot again. The database also verifies legal transitions, prohibits terminal changes and checks the command against the revision. Replays return the exact response for the original command. Three total attempts are allowed on deadlock, serialization conflict and lock timeout with jitter. An ambiguous connection/commit failure propagates. The pending request survives to retry the same operation. [State machine](../packages/database/src/postgres-original-sessions.ts#L154) · [Retry/commit](../packages/database/src/postgres-original-sessions.ts#L190) · [Browser recovery](../apps/web/src/components/casino/original-player.tsx#L67)
- **Test and mitigation.** Count version conflicts separately from infrastructure errors. Race reveal/reveal and reveal/finish from separate API processes. Interrupt before commit, discard a post-commit reply, saturate pool acquisition, then require one matching revision/command and owner-scoped recovery. Use snapshots to update the local UI before a background reconciliation where safe. Retain authoritative version checks, private-state isolation and session identity. Measure API p95 <150 ms separately from preflight/refetch and separate time awaiting a conflict from successful action time.

### H. Recovery and casino history

- **Observed.** The practice room queries session and history on entry/focus. `GET /casino/demo/session` reads the namespace. The list endpoint independently reads it again and returns up to 50 public snapshots for one player, optionally one game, ordering active first, then time and ID descending. The get-by-ID endpoint adds the owner predicate and projects public result only. Reads are private/no-store. The player/game/time/ID index omits the active ordering expression. Without a game filter, game precedes timestamp in the index. Each list can therefore require filtering/sorting many candidate rows before returning 50. There is no per-round N+1 query in this store. A 50-row response limit bounds neither historical storage nor all DB work. ### J. Bet and transaction history

- **Observed.** Bet list filters by authenticated user, reads full JSONB records, sorts on JSON text `createdAt` without a tie-breaker and returns the entire list. Its composite PK starts with player but does not match this sort. Bet detail fetches the same list. The browser filters and sorts locally. Wallet history executes the grant, loads all journals for all players, filters in memory, maps rows, then calls `paginate`. A public page size of 10/50 therefore does not protect DB or Node memory. Ledger header sorting only by `createdAt` also lacks a deterministic tie-breaker. ## Database guarantees and production gates

1. **Journal sealing and checks.** Initial SQL makes headers/entries/audit append-only, checks simulated-only headers, positive amounts and balancing. Phase 7 seals past journals with nullable historical posting XID, requires future entries to share the creating transaction's full XID, checks immutable account currency under row lock, and defers the per-wallet nonnegative aggregate. Final hardening also checks every inserted line's entire journal and advances a private account revision fence for each line. These checks cover direct concurrent SQL writers subject to the tested runtime grants. Repeated wallet SUMs still grow with one wallet's lifetime entries. Repeated journal aggregates grow with line count, bounded at 32 for normal domain posts. Profile deferred-trigger commit time separately from statement time. Never drop integrity guards solely to hit a latency SLO. [Sealing](../packages/database/prisma/migrations/20261103020000_financial_integrity/migration.sql#L19) · [Fences](../packages/database/prisma/migrations/20261103140000_financial_hardening/migration.sql#L25) · [Domain limit](../packages/domain/src/ledger/validate.ts#L14)
2. **Hot accounts and retries.** Sorted advisory account locks coordinate even absent account rows. Row locks and revision updates serialize shared house accounts across unrelated players, and the DB may abort stale serializable snapshots. Separate grant, ordinary win/loss and heavily reused house scenarios. Report block duration, lock order, retries/exhaustion and useful committed TPS rather than attempted TPS. Keep all posting effects local to each retryable unit. The current financial retry classifier recursively matches P2034/P2002/40001/40P01. Verify once-only client effects on true commit ambiguity and distinguish a unique payload replay from a persistent constraint defect. If a shared clearing account eventually limits capacity, evaluate an explicitly reconciled/accounting-approved account topology on an isolated fixture after measuring the scoped-query change. [Account locking](../packages/database/src/prisma-ledger-store.ts#L64) · [Retry classifier](../packages/database/src/prisma-ledger-store.ts#L182) · [House accounts](../packages/domain/src/wallet/demo-wallet.ts#L9)
3. **Connection budgets.** Ledger, player directory and bets instantiate separate Prisma adapters. Casino has an independent pg pool capped at 10 per API replica. Readiness creates/disconnects a Prisma client per database check. Compose sets PgBouncer transaction mode, default server pool 20 per pool and 200 client connections. These are local settings. Derive a budget from number of replicas × actual pools and maxima, database/users, workers, probes, migrations and reserved failover/admin capacity. Instrument client checkout vs PgBouncer waits vs PG lock waits. Share the intended runtime adapter lifecycle where possible and give readiness a tiny bounded cost. Transaction-level advisory locks and SET LOCAL fit transaction pooling, as each transaction stays on one backend until commit. Verify exact Prisma/pg protocol, prepared-statement behavior and workload on this PgBouncer version. Do not rely on state surviving between transactions. Require a direct privileged migration connection and a separate runtime role. [Wiring](../apps/api/src/player/player.module.ts#L43) · [Ledger module](../apps/api/src/ledger/ledger.module.ts#L25) · [Adapters and ping](../packages/database/src/prisma.ts#L5) · [Compose pools](../docker-compose.yml#L23)
4. **Five migrations and upgrade safety.** The initial migration creates the ledger. The second adds auth and sessions. Financial integrity adds XID sealing and durable bets. Financial hardening adds fences, locked revalidation and the readiness marker. The fifth adds the isolated casino tables. The auth migration adds nullable names/password hashes then immediately requires both, **without backfill**. A legacy populated initial users table cannot pass that step. Inventory such databases and design an identity recovery/backfill procedure appropriate to the provenance of those users. Add an occupied legacy fixture before certifying an upgrade. Preserve checksums of applied migrations. The last financial migration takes ACCESS EXCLUSIVE across five tables before scanning, under 10 s lock / 120 s statement timeout. Drain incompatible writers over the full chain, including the preceding migration. Rehearse on a restored large clone, capture duration, lock blockers, space/WAL and rollback. A constant-return readiness marker proves that the migration function exists. It cannot detect subsequent operator DDL or grant drift. Verify schema hashes, triggers and grants independently. On failure keep writes closed and roll forward from a verified version. 5. **Reconciliation and access.** Algebraic balance alone cannot detect a duplicated business event encoded under different keys or a missing compensating posting. Add periodic owner/currency net checks, journal↔bet/status/hold mapping, command↔casino-revision checks, immutable exception reports, a reviewed correction workflow and separate restricted runtime/migration/operator roles. A snapshot of account revisions is concurrency metadata only. Prove posted journals and actor-bound audit records are consistent on both success and rollback. The implementation emits a status audit on actual state changes. An internal deferred acceptance never gets a public operator endpoint in this revision. The current application identifies players, with no tenant dimension in bet/round uniqueness. Require an explicit tenancy and operator trust model before multi-operator use. 6. **Retention and partition strategy.** Casino command responses are immutable per revision. Rounds deny deletion and their owner FK restricts deletion. JSON replay snapshots, audit/log growth, session expiry and WAL therefore need explicit retention policies, access controls, storage forecasts and restore tests. Measure bytes per distinct player/round/reveal and aged account, retention duration, growth, update bloat and autovacuum workload before proposing time partitions. Moving replay rows must preserve global key uniqueness and full response history across partitions or archives. Never delete a key while an otherwise valid retry could reapply a committed effect. Resolve account erasure, pseudonymization and immutable record obligations with the applicable operator and jurisdiction. Drill encrypted base backups, archived WAL, point-in-time recovery, key retrieval, promotion and failback in isolation.
